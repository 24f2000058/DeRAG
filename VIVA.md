# DeRAG — Viva Preparation

Anticipated oral-exam questions and answers, organised by the three subject
areas of the academic overview — Deep Learning, Information Storage &
Retrieval, Blockchain. Every answer is grounded in a decision the team
actually made and recorded: see `DECISIONS.md` (one dated entry per
milestone, 0–10) and the commit history. Nothing here is post-hoc
rationalisation — where a choice turned out to be wrong or incomplete, the
answer says so and describes how it was caught and fixed.

The measured numbers come from `eval/results.md` and
`eval/hallucination_qualitative.md` (Milestone 10), regenerated by
`scripts/evaluate.py` from a clean pipeline run.

## Deep Learning

### Why `all-MiniLM-L6-v2` for embeddings?

It is small, fast, runs locally on CPU, and produces 384-dimensional
vectors (Milestone 1). The whole project has a no-cloud-API runtime stance,
so the embedding model has to load once (cached at `~/.cache/huggingface`
after first download) and then work fully offline. `pipeline/embeddings.py`
owns both the encoder and `cosine_similarity`, so ingest-time and
query-time vectors are produced by the exact same code path. The model's
built-in `Normalize` module L2-normalises every vector to unit norm, which
is why cosine similarity and L2 distance rank identically over this corpus
— a fact that let Milestone 2 pick a Chroma distance function without it
affecting ranking output.

### Why are embeddings pre-computed by the pipeline instead of letting Chroma embed?

Every collection is opened with `embedding_function=None` (Milestone 2).
The pipeline computes vectors with `pipeline/embeddings.py` and hands them
to Chroma explicitly. This was verified to actually disable Chroma's
default ONNX auto-embed, not merely decline to configure one: calling
`add()` with `documents=` but no `embeddings=` raises
`ValueError: You must provide an embedding function`. The reason is
correctness of the experiment — if Chroma embedded with its own bundled
model, ingest and query would use different embedding code, and the
Standard-RAG-vs-DeRAG comparison would no longer be measuring only the
rerank layer. Keeping one embedding implementation also keeps Milestone 4's
IPFS re-hash round trip meaningful, because the text that gets hashed,
embedded, and stored is one canonical normalised form.

### Why 500-character chunking, and what did it cost?

`pipeline/chunking.py` uses `RecursiveCharacterTextSplitter` from
`langchain_text_splitters` with a 500-character split ceiling (Milestone
1). `normalize_text()` collapses all whitespace — including blank-line
paragraph breaks — to single spaces before chunking, so the splitter's
`"\n\n"` / `"\n"` separator levels are dead and boundaries fall through to
word level. That is a deliberate tradeoff: the Milestone 4 hash-stability
contract needs exactly one canonical normalised form, and paragraph-aware
chunking would require changing that contract and re-reviewing Milestone 4.
The 500-char ceiling is also the constraint that forced the Milestone 9
corpus truncation — `seed_reputation.resolve_doc_hash` requires exactly one
chunk per file, real SciFact abstracts run 600–2000 characters, so every
corpus file is stored as a leading-sentence excerpt truncated to ≤480
characters. That truncation is the root of the "hardest question" below.

### Why `gemma4:12b` and not the spec's Phi-3-mini or Llama-3-8B?

All three are open-weight and open-license, so the no-cloud-API stance did
not decide it — the choice was quality-versus-memory on the real target
machine: 7.6 GB total RAM, RTX 4060 with 8 GB VRAM (Milestone 7). Plain CPU
inference was measured and rejected outright — a 90-second timeout, free
RAM collapsing to 82 MB, heavy swap thrashing, unusable. GPU offload
without the tuning below was viable but mediocre at roughly 24 tokens/s.
`gemma4:12b` (Q4_K_M, 11.9B params) was already pulled locally and, once
GPU-offloaded with the systemd tuning applied, answers in about 1–2 seconds
with no visible quality loss from quantization pressure — a materially
better quality/memory tradeoff on this specific box than pulling either
spec-listed alternative fresh. Milestone 10's live window re-confirmed the
box is VRAM-bound even with tuning: `ollama ps` shows a 23% / 77% CPU/GPU
split because the 7.9 GB model plus KV cache exceeds 8 GB VRAM.

### Why `think: false` and why target `/api/chat` instead of `/api/generate`?

`gemma4:12b` is a thinking model. Without `think: false` its real answer
text first lands in a separate `message.thinking` field, and a capped
`num_predict` can be exhausted mid-thought before any text reaches
`message.content` — which showed up in early testing as an apparent "empty
response" bug that was actually a token-budget-and-mode issue, not a
serialization bug (Milestone 7). `think: false` is a `/api/chat`-only
parameter, so generation targets `POST /api/chat`, not `/api/generate`
(whose response field is named `response`, not `message.content`). This was
confirmed live on both blocking and streaming calls, not taken from docs.

### The Ollama systemd tuning — why is it required and why is it not in the repo?

`gemma4:12b` is only viable on the demo machine with a
`/etc/systemd/system/ollama.service.d/override.conf` drop-in setting
`OLLAMA_NOPRUNE=1`, `OLLAMA_KV_CACHE_TYPE=q8_0`,
`OLLAMA_FLASH_ATTENTION=1`, `OLLAMA_KEEP_ALIVE=-1`, then
`daemon-reload` + `restart ollama` (Milestone 7). It lives outside the
repo because it is OS service configuration, not something
`pyproject.toml`, `.env.example`, or any Python-managed file can carry.
The important property is that a missing override is a **silent
performance regression, not a crash**: a fresh machine without it falls
back to CPU inference or slow partial GPU offload and still answers, just
badly. A common failure mode was verified live — omitting the `[Service]`
header line when pasting into the `systemctl edit` buffer makes systemd
ignore every line ("Assignment outside of section" in the journal) while
the service still reports `active`. Milestone 10's README now carries the
whole block verbatim including that header and the restart step.

### How is on-chain reputation turned into a score the ranker can use?

`normalize_reputation()` in `retrieval/rerank.py` applies a fixed sigmoid,
`1 / (1 + exp(-reputation / SCALE))` with `SCALE = 10` — a fixed global
curve, deliberately **not** per-batch min-max normalisation (Milestone 6).
Two reasons, both recorded at the time. First, Milestone 10's MRR /
Precision@K evaluation needs a document's trust contribution to be
identical across queries; per-batch min-max would make the same chunk
normalise differently depending on which unrelated candidates happened to
land in that query's top-K, conflating the document's own reputation with
the incidental composition of the candidate set. Second, min-max
degenerates (divide-by-almost-zero) when all K candidates share similar
reputation and needs a special-cased fallback that the sigmoid does not.
Unregistered chunks (`exists=False`) are floored `FLOOR_PENALTY = 50` below
the batch minimum, because on-chain reputation `0` is the neutral value
that `registerDocument()` assigns every freshly-published document — a
chunk with no on-chain record at all is a strictly weaker provenance
signal than a registered-but-neutral one and must sort below it.
`FLOOR_PENALTY = 50` was picked relative to `SCALE = 10` (five
half-widths) so the floor saturates near 0 regardless of the batch
minimum; an earlier `FLOOR_PENALTY = 1` was rejected in design because its
roughly 0.025 normalised gap was too small to survive a realistic
similarity-score gap.

### How was `alpha = 0.7` chosen and validated?

The hybrid score is `alpha * similarity + (1 - alpha) * normalized_reputation`.
`alpha = 0.7` was pinned in Milestone 6 from synthetic validation, with an
explicit "domain mismatch" caveat to revisit against real data — `similarity`
runs `[-1, 1]` (mildly negative cosine values for unrelated text are
routine with this embedding model) while `normalized_reputation` is bounded
`(0, 1)` by the sigmoid, so it is not a literal 70/30 blend of two
equally-scaled terms. Milestone 9 confirmed the ranking constants did not
need retuning against the real corpus. Milestone 10 turned that assertion
into a measurement: the alpha sweep over `0.0, 0.3, 0.5, 0.7, 1.0` across
all three real queries gives MRR@10 = 1.000 at alpha 0.0, 0.3, 0.5, and
0.7 — a **wide plateau** — and drops to MRR@10 = 0.667 only at alpha 1.0.
So `alpha = 0.7` sits on a flat maximum, not a knife-edge tune. The alpha
1.0 row is a built-in sanity check: it collapses the hybrid score to pure
similarity and therefore reproduces Standard RAG's MRR (0.667) exactly.
The plateau extends all the way to alpha 0.0 (pure reputation) because the
three legit targets each sit in the candidate window at +10 against their
poison at −50, so reputation alone already ranks them first. That the
plateau reaches 0.0 is a statement about the seeded reputation spread on
these three queries, not evidence that the similarity term is redundant —
see "If even `alpha = 0.0` scores a perfect MRR" under Information Storage
& Retrieval.

## Information Storage & Retrieval

### Why SciFact rather than Climate-FEVER?

The assignment's "Class 1" evidence is worded as "peer-reviewed abstracts
or verified claims". SciFact (`allenai/scifact`, CC-BY-NC-2.0) pairs an
expert `claim` with a peer-reviewed `abstract` — a direct match.
Climate-FEVER's evidence is Wikipedia sentences, which is not (Milestone
9). The corpus is built from the real SciFact S3 release archive
(`scifact.s3-us-west-2.amazonaws.com/release/latest/data.tar.gz`), not
paraphrased from model training knowledge, because the Hugging Face
dataset viewer runs custom loader code and was unavailable.
`scripts/build_demo_corpus.py` regenerates it deterministically —
byte-identical `manifest.json` across runs.

### What is the vector store and distance metric?

Local-persistent ChromaDB (`chromadb` 1.x, pinned deliberately — the
`>=0.5` floor in `pyproject.toml` resolved to 1.5.9 and the code is
written against the 1.x client API), cosine space, set via
`configuration={"hnsw": {"space": "cosine"}}` on
`get_or_create_collection()` (Milestone 2). This was verified against the
real install, not assumed: `collection.configuration_json` echoes the
setting back and two orthogonal unit vectors return `distance = 1.0`
(cosine) rather than `2.0` (squared-L2). The Chroma document ID is
Milestone 1's SHA-256 of the normalised chunk text, and storage always
uses `upsert()`, so re-ingesting byte-identical content overwrites in
place — though that idempotency is a coincidental consequence of upsert
semantics, not a designed guarantee, which is why on-chain
registration has its own explicit duplicate-hash check. Standard RAG
(`retrieval/standard_rag.py`) is pure cosine top-k with no reranking — the
baseline the whole thesis is measured against.

### The single-chunk-per-file constraint and the leading-sentence truncation — what is the trade?

`pipeline/chunking.py` splits anything over 500 characters and
`seed_reputation.resolve_doc_hash` requires exactly one chunk per file, so
every corpus file must fit a single chunk. Real SciFact abstracts run
600–2000 characters (the shortest in the eligible pool was 617), so
`build_demo_corpus.py` stores every abstract — all 47 filler and the 3
poison-targeted legit — as a **leading-sentence excerpt truncated to ≤480
characters** via `fit_to_single_chunk`, i.e. the OBJECTIVE / DESIGN
sentences with the results and conclusion cut off (Milestone 9). The plan's
original `eligible()` filter gated its length check on the *raw* abstract
and therefore matched zero documents; it was controller-ratified to gate
on the fitted text instead. The consequence is that the spec's "50
unmodified abstracts" are in practice 50 truncated leading-sentence
excerpts, and leading-sentence (rather than results-preserving) excerpting
is the mechanical reason two of the spec's three §2 similarity orderings
flipped. A results-aware excerpt would likely have preserved them without
touching `chunk_size` — this was deferred and is discussed under the
hardest question.

### Why is `source_doc_id` in the manifest, and why `null` for poison chunks?

`manifest.json` carries per-chunk ground truth: `chunk_id`,
`source_doc_id` (added in Milestone 10 Task 1 — the SciFact document id as
a string), `is_poisoned`, `publisher_key`, `target_reputation`,
`target_queries`, `ground_truth_chunk_id`. `source_doc_id` is the field
the evaluation uses to decide relevance: a retrieved hit counts as
relevant iff its `source_doc_id` matches the query's one ground-truth
SciFact document. It is `null` for the fabricated `FABRICATED_MISINFO_*`
chunks because a poison chunk did not come from any SciFact document —
there is nothing truthful to point at. The "this fabrication attacks that
topic" link already exists separately as `ground_truth_chunk_id`, so
`null` here is precise, not missing data. Poison chunks are never relevant
under any query.

### What is the candidate-window pre-flight and why does it exist?

`scripts/check_candidate_window.py` (Milestone 9 spec §3a). Before the
regression test or the evaluation can rely on rerank margins, it confirms
that for each target query BOTH the poison chunk AND its legitimate
counterpart appear in `vector_store.query(q, k=10)`. The reranker can only
differentiate chunks it actually receives, so if a relevant chunk fell
outside the retrieval window the rerank result would be meaningless. It
prints `[preflight] PASS` on every run and `k_retrieve` never had to be
raised above 10.

### What does the retrieval evaluation measure, and what is the result?

MRR@10 plus Precision@1 and Precision@3 for both retrieval modes across the
three target queries, ground truth from `manifest.json` — one relevant
SciFact document per query (Milestone 10). The metrics use a `k_return=10`
override; the product/UI default stays `k_return=3`. It is deliberately a
**two-positive / one-honest-negative** design: two topics where a poison
chunk beats the truth on raw similarity (TMAO, H. pylori) and one where it
does not (antibiotics), kept as a no-regression check.

| Query | SR P@1 | DeRAG P@1 | SR RR | DeRAG RR |
|-------|-------:|----------:|------:|---------:|
| TMAO / red meat | 0.000 | 1.000 | 0.500 | 1.000 |
| H. pylori / gastric cancer | 0.000 | 1.000 | 0.500 | 1.000 |
| antibiotics / C. difficile | 1.000 | 1.000 | 1.000 | 1.000 |

Mean MRR@10 — **Standard RAG 0.667, DeRAG 1.000**. P@3 is 0.333 for every
row because there is only one relevant document per query, so 1/3 is the
ceiling at k=3 — P@1 and RR are the discriminating metrics. On TMAO the
poison beats the real abstract on cosine by roughly 0.198 (a wide margin);
on H. pylori by roughly 0.046 (thin); on antibiotics the legit excerpt
still edges the fabrication, 0.7329 versus 0.7092 (margin 0.0237), so
Standard RAG is already correct there and DeRAG correctly leaves the order
alone.

### If even `alpha = 0.0` scores a perfect MRR, is the hybrid design actually being tested?

It is a fair challenge, and the honest answer is that the *evaluation set*
does not test it — the *design* is unchanged. All three evaluation queries
target chunks that were given a deliberately decisive on-chain reputation
spread: the legitimate document at +10, its poison counterpart at −50.
That spread was seeded on purpose, to demonstrate that the mechanism *can*
override a similarity-based fooling attempt. A consequence is that at
`alpha = 0.0` the reputation term alone already separates every relevant
document from its poison, so the sweep's plateau down to 0.0 shows the
reputation signal is decisive on these three queries — it does not show
the similarity term carrying a ranking on its own.

The case the current evaluation never exercises is *uninformative*
reputation. The 47 filler chunks all sit at reputation 0, tied; for any
query whose ground-truth answer is one of those neutral chunks, the
`(1 - alpha)` reputation term contributes nothing to the ordering and the
`alpha * similarity` term has to do all the work. The hybrid formula is
built for exactly that fallback — as reputation ties or goes neutral it
degrades to similarity-ranked retrieval — but none of the three target
queries put it in that regime. Milestone 6's synthetic validation did
cover mixed and neutral reputation; the Milestone 10 real-data evaluation
deliberately traded that coverage for a clean poisoning-resistance proof
on real abstracts. It is a scope limitation of the evaluation set, stated
in `DECISIONS.md`, not a gap in the ranking design — and it is the first
of the two items a v2 evaluation should close (see the final section).

### Be honest about H. pylori: does DeRAG actually fix the generated answer?

Not fully, and the write-up says so (`eval/hallucination_qualitative.md`).
Retrieval flips cleanly — DeRAG's rank-1 context for H. pylori is the real
abstract, P@1 goes from 0.000 to 1.000. But the *generated* DeRAG answer
does not reach a clean "Yes" the way TMAO's does; it degrades only to an
unresolved both-sides hedge that still presents the fabricated "protective,
odds ratio 0.36" claim as one side. Two compounding, on-record reasons:
(1) the real H. pylori chunk is truncated to its objective/design sentence
with no results (the Milestone 9 leading-sentence truncation), so it
carries the question but not the finding; (2) after rerank the −50 poison
chunk still occupies context slot #2 of the 3-item window — trust-weighting
fixes rank-1, not membership. For contrast, Standard RAG's H. pylori answer
is a confident, unambiguous hallucination — it states outright that
infection is "protective rather than causative" with an odds ratio of 0.36
— and DeRAG's TMAO answer *is* a clean unhedged correct affirmative.
Reporting the hedge rather than hiding it is the honest result: H. pylori
is the thinner-margin, more drift-exposed case at both the retrieval and
the generation level.

### IPFS and content-addressing — what does it actually guarantee?

Chunk bodies live on IPFS, uploaded via the API's `/api/v0/add` (Milestone
4). `verify_hash()` re-hashes fetched content with Milestone 1's exact
`hash_chunk` — hashing the fetched bytes **verbatim**, never re-running
`normalize_text` — so a match proves the content served for a CID is
byte-identical to what was registered. Fetch is via the public gateway
(`GET :8080/ipfs/<cid>`), not the API's `/api/v0/cat`, because the gateway
is a plain bodyless GET and is the same read-only surface Milestone 8's
audit UI uses; that UI's "Hash match / Hash MISMATCH" badge is built
directly on `verify_hash()`. Kubo's `/api/v0/*` endpoints were confirmed
live to reject GET with 405, so every API call including reads is POST.
Retrieval itself only needs Chroma plus the chain — IPFS is on the
ingest/seed path and the audit display, not the query hot path.

## Blockchain

### Why a blockchain here at all — what does it buy you?

The thesis is that a provenance/reputation signal that lives outside the
vector store can override similarity when similarity is being gamed. The
chain is the tamper-evident ledger for that signal: `registerDocument`
records a document's content hash, IPFS CID, and publisher; `updateReputation`
is the oracle-gated channel that moves a document's score. The evaluation
is exactly this claim under test — Standard RAG (similarity only) scores
MRR@10 0.667 against DeRAG's 1.000 because the on-chain −50 on each poison
chunk is what flips the two fooling cases back.

### Why a local Hardhat chain, and what happens on restart?

Local Hardhat only, no public deployment — this is an MVP and every chunk
would otherwise cost real gas (Milestone 9). The chain state is in-memory
and does **not** survive a node restart: a restart means redeploy plus
re-seed. This was hit for real in the Milestone 10 live window when a
model-load memory spike OOM-killed the Hardhat node; the recovery was
redeploy + reseed + rerun, after which `scripts/evaluate.py` reproduced
`eval/results.md` byte-identically. `contracts/scripts/deploy.ts` writes
`contracts/deployments/localhost.json` on every deploy and
`registry_client.py` reads the address straight from that file, so a fresh
`npx hardhat node` needs no manual address copying.

### Contract design — `DeRAG_Registry.sol`.

An owner/oracle-gated reputation ledger (Milestone 3). `address public
owner` is set to `msg.sender` in the constructor, which also
auto-authorizes the deployer as the first oracle
(`authorizedOracles[msg.sender] = true`) — matching the spec's "Account #0
is Admin/Oracle" framing, since Account #0 is the deploying account in the
standard Hardhat workflow. `updateReputation` is `onlyAuthorizedOracle`.
`authorizeOracle(address, bool)` is owner-gated so more oracles can be
added without a redeploy. `registerDocument` **reverts on a duplicate
`doc_hash`** rather than silently no-opping, protecting on-chain integrity
even if called out-of-band — the ingestion script is responsible for
calling `get_document()` / `verify_integrity()` first to avoid wasting gas
on an expected revert. The publisher address is recorded per document. The
auto-generated `documentLedger` getter was confirmed (by compiling a
scratch contract and inspecting the ABI) to return all six struct fields —
publisher, contentHash, ipfsCID, reputationScore, timestamp, isRegistered
— so no separate getter was written.

### Publisher attribution — does the ranker use it?

No. `trust_weighted_rerank` **never reads `publisher`** (Milestone 9).
Poisoning resistance operates entirely on per-`doc_hash` reputation, not
on identity. The publisher assignment — filler to Hardhat Account #1, the
3 poison-targeted legit sources to Account #2, the 3 fabricated chunks to
Account #5, oracle to Account #0 — is demo-narrative only: it makes the
audit-trail UI tell a coherent story about who published what, but it has
zero effect on ranking. If every chunk were published from one account the
evaluation numbers would be unchanged.

### How is reputation seeded, and is it safe to re-run?

`scripts/seed_reputation.py` reads each chunk's current on-chain
reputation via `get_document`, computes `delta = target - current`, and
skips anything already at target (Milestone 9). `manifest.json` stores an
absolute `target_reputation` per chunk using Milestone 6's validated
synthetic magnitudes: poison `-50`, poison-targeted legit `+10`, filler
`0`. Because it works in deltas against observed state, re-running is a
no-op — verified on both full runs: the 47 filler chunks logged
`[seed] skip` with zero transactions and only the 6 non-zero-target
chunks were written. That idempotency is what makes the redeploy + reseed
recovery after a node restart reliable.

## The hardest question

**"Antibiotics behaves differently from TMAO and H. pylori — how do you
know that's a real, honest result and not cherry-picked?"**

The honest answer is the actual sequence of events, because the antibiotics
case is not a result we designed for — it is the residue of a mistake the
process caught and corrected, and the correction is what makes the whole
evaluation trustworthy. Five steps, all on record in `DECISIONS.md`
(Milestone 9 section plus its post-merge follow-up note) and the Milestone
9 commit history.

**1. The single-chunk ingestion constraint forced truncation.**
`seed_reputation.resolve_doc_hash` requires exactly one chunk per file and
`pipeline/chunking.py` splits anything over 500 characters. Real SciFact
abstracts are 600–2000 characters, so `build_demo_corpus.py` stores each
one as a leading-sentence excerpt (`fit_to_single_chunk`, ≤480 characters)
— OBJECTIVE / DESIGN sentences with the results and conclusion removed. The
plan's original `eligible()` filter checked length against the raw
abstract and so matched zero documents; it was controller-ratified to gate
on the fitted text instead.

**2. Truncation mechanically flipped 2 of the 3 designed similarity
orderings.** The spec's §2 similarity numbers were measured on whole
abstracts. A leading OBJECTIVE sentence is less similar to a
results-oriented question than the full abstract is. Against the truncated
corpus files:
- TMAO: poison 0.779 vs legit 0.581 — poison wins by roughly 0.198 (wide).
- H. pylori: poison 0.802 vs legit 0.756 — poison wins by roughly 0.046.
  This is the **opposite** of spec §2a's whole-abstract ordering
  (legit 0.830 > poison 0.803): truncation flipped it.
- antibiotics: legit 0.7329 vs poison 0.7092 — **legit wins** by 0.0237.
  Under its natural query the truncated real excerpt still edges the
  fabrication.

So antibiotics did not become the "honest negative" by design — the
truncation that flipped the other two simply did not flip this one. That
is the point: the excerpting rule was applied uniformly, and the outcome
per query is whatever the data does.

**3. `DEMO.md` was found still describing the pre-truncation framing, and
was corrected.** During the H. pylori work it was noticed that `DEMO.md`
still presented H. pylori as a non-fooling, reputation-layer-only case
(the original spec framing) even though the live measurement now had the
poison winning retrieval. `DEMO.md` was rewritten to describe H. pylori as
a second real fooling case and antibiotics as the deliberate non-fooling
contrast.

**4. H. pylori's flip was re-examined and promoted to a hard regression
case.** It had been measured *and* direction-tested in
`tests/test_demo_corpus_fixtures.py`, but it had never been parametrized
into the retrieval-regression assertions in
`tests/test_demo_corpus_regression.py` — a measured-but-not-asserted
oversight, not a scope decision. Commit 8605591 promoted it across all
three assertions (`test_standard_rag_top1_is_the_poison_chunk`,
`test_trust_weighted_top1_is_not_a_poison_chunk`,
`test_trust_weighted_ranks_legit_counterpart_above_its_poison`), so the
thesis proof now rests on **two independent queries**, not one. The fresh
full-pipeline run after promotion was `7 passed, 1 xfailed`.

**5. Doing that rigorously surfaced a test-isolation bug.** The original
regression test was monolithic: it parametrized BOTH "Standard RAG is
fooled" AND "trust-weighted rerank demotes the poison" under a single
`xfail(strict=False)` for the antibiotics case. Because antibiotics does
not fool Standard RAG, the whole test was xfail for that case — which
would have **silently masked a genuine DeRAG regression** on the
antibiotics query riding alongside the expected Standard-RAG failure.
Commit 514fdd1 fixed it by splitting the trust-weighted assertion into its
own test, `test_trust_weighted_top1_is_not_a_poison_chunk`, that runs
**unconditionally for all three queries with no xfail on any of them**. So
antibiotics still hard-asserts that DeRAG's top-1 is not a poison chunk.

**Why this is a strength, not a confession.** The process caught its own
mistakes and the evaluation got stronger: two independent hard fooling
cases plus one honest non-fooling contrast, with tighter test isolation. A
mechanism that also fires correctly when it is *not* needed — antibiotics,
where DeRAG leaves the already-correct order alone and the generated answer
is identical under both modes — is more trustworthy than one that only
ever "succeeds", because the antibiotics case is the one you can
hand-verify end to end before trusting the mechanism on cases you cannot.
The alpha sweep is the same kind of evidence: MRR@10 is 1.000 across alpha
0.0–0.7 and drops to exactly Standard RAG's 0.667 at alpha 1.0, so the
shipped `alpha = 0.7` is a point on a flat maximum with a built-in sanity
check at the endpoint, not a tuned-to-fit number.

## Limitations and what a v2 would address

Two findings from Milestone 10 are disclosed rather than smoothed over,
and they point at the same next step.

**1. The evaluation does not exercise uninformative reputation.** All
three target queries use a decisive seeded reputation spread (+10 vs −50),
so the reputation term alone separates every relevant document from its
poison and the sweep plateau reaches `alpha = 0.0`. No query in the set
has its ground-truth answer among the 47 neutral (reputation 0, tied)
filler chunks, which is the regime where the `alpha * similarity` term
must carry the ranking under the hybrid formula. A v2 evaluation should
add at least one query whose relevant document is a neutral-reputation
chunk, to measure similarity-carried ranking with the hybrid score in
effect — Milestone 6's synthetic tests covered this; the real-data set
traded it for a clean poisoning-resistance proof.

**2. Trust-weighting fixes retrieval rank, not the generation context.**
On H. pylori, DeRAG promotes the real abstract to rank 1 but the −50
poison chunk still sits at slot #2 of the 3-item context window, and the
generated answer degrades only to a both-sides hedge rather than a clean
correction. A v2 would carry the trust signal past retrieval into
generation — e.g. drop or down-weight a heavily-demoted chunk from the
prompt context rather than only from the top rank, and/or surface each
source's trust score into the prompt so the model can weight the
conflict itself. This also interacts with the single-chunk truncation
