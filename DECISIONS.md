# DECISIONS

## Milestone 0 — Project Scaffolding (2026-08-14)

- **Python dependency manager: `uv`.** Already installed on the dev
  machine; single `pyproject.toml` + `uv.lock`; `uv run` manages the venv
  without manual activation.
- **Python version: 3.11**, pinned via `.python-version`. Chosen over the
  system's 3.12 for broader wheel availability across
  sentence-transformers/torch/chromadb/langchain.
- **Hardhat language: TypeScript.** Config, deploy scripts, and contract
  tests are all `.ts`.
- **Node package location: nested inside `/contracts`** as its own
  self-contained npm package, isolating the Node toolchain from the
  Python side of the repo entirely.
- **Folder layout: flat Python package tree at repo root**
  (`pipeline/`, `retrieval/`, `blockchain/`, `storage/`, `generation/`,
  `scripts/`, `app/`) under one `pyproject.toml`, since a single Python
  process spans all of them at runtime. `/contracts` is the one exception,
  kept as an isolated npm package.
- **Test placement: single top-level `/tests/` directory**, files named
  `tests/test_<module>_<thing>.py`, no per-module `tests/` subfolders.
  Chosen to keep pytest discovery to one root and avoid re-deciding
  placement ad hoc in every later milestone.
- **Test frameworks:** `pytest` for Python, Hardhat's native Mocha/Chai
  (via `hardhat-toolbox`) for Solidity.
- **ChromaDB 1.x, not 0.5.x.** `pyproject.toml` pins `chromadb>=0.5` with no
  ceiling; `uv.lock` resolved it to `1.5.9`. This is intentional — the
  installed and target API is ChromaDB 1.x, not the 0.5.x line the floor
  might suggest. Recorded here so later milestones write retrieval code
  against the 1.x client API without needing to re-discover this.

## Milestone 1 — Preprocessing Pipeline (2026-08-15)

- **`normalize_text()` algorithm (hard contract for Milestone 4's IPFS
  re-hash round trip):** `unicodedata.normalize("NFKC", raw)` → strip
  Unicode categories `Cc`/`Cf` except `\t`/`\n`/`\r` (via a precomputed
  `str.translate` removal table) → collapse whitespace runs to a single
  space and strip ends (`re.sub(r"\s+", " ", text).strip()`) → `.lower()`.
  NFKC runs first so it folds exotic whitespace (e.g. NBSP) to regular
  space before the control-char strip and whitespace collapse run, and so
  it folds compatibility/full-width variants before lowercasing. Verified
  idempotent: `normalize_text(normalize_text(x)) == normalize_text(x)`.
  Milestone 4 must hash fetched chunk text **verbatim** (never re-run it
  through `normalize_text`) — `hash_chunk` only ever hashes the exact
  string it's given, so the two hashes match by construction as long as
  that invariant holds.
- **`langchain-text-splitters` is now a direct dependency**
  (`pyproject.toml`, `>=1.1`, resolved to 1.1.2 in `uv.lock`), not just a
  transitive pull via `langchain-community` (which prints a
  sunset/deprecation warning on import as of 0.4.2). Import path:
  `from langchain_text_splitters import RecursiveCharacterTextSplitter`.
- **`all-MiniLM-L6-v2` downloads on first use**, cached at
  `~/.cache/huggingface` afterward. One-time network dependency for this
  milestone only (and any future fresh environment); everything after the
  first load is fully offline, consistent with the project's "no cloud
  APIs" runtime stance.
- **`ingest_prep()` record shape is locked**: `{"chunk_id": int, "text":
  str, "hash": str, "embedding": list[float]}`, `chunk_id` is a 0-based
  sequential index per call. Milestone 5's ingestion script consumes this
  shape directly — do not rename these fields without updating Milestone 5.
- **Chunking loses paragraph-boundary awareness by design.** `normalize_text()` collapses
  all whitespace (including blank-line paragraph breaks) into single spaces before
  chunking, so `RecursiveCharacterTextSplitter`'s `"\n\n"`/`"\n"` separator levels are
  always dead in this pipeline — chunk boundaries fall through to word-level splitting,
  which can cut mid-sentence. This is a known, deliberate tradeoff (required for the
  Milestone 4 hash-stability contract, which needs one canonical normalized form) — not
  a bug. If paragraph-aware chunking becomes a priority, it requires a normalization
  contract change and a full Milestone 4 impact review, not a quick fix here.
- **Embedding vectors are L2-normalized** (unit norm) by the model's built-in `Normalize`
  module — cosine similarity and L2 distance will rank identically over these vectors,
  relevant when a later milestone picks a ChromaDB distance function.
- **`chunk_id` is per-call only, not globally unique.** A future milestone ingesting
  multiple documents will need a way to attribute chunks to their source (e.g. adding
  a `source` key to the record) — flagged now as the intended extension point, not
  discovered under pressure later. The current four-key shape stays locked until that
  milestone explicitly extends it.

## Milestone 2 — Vector Store & Retrieval (2026-08-15)

- **Chroma document ID = `record["hash"]` (Milestone 1's sha256 of the normalized
  chunk text), used directly** instead of inventing a new ID scheme. It's already
  unique per content, so no extra bookkeeping is needed, and it sidesteps
  Milestone 1's flagged caveat that `chunk_id` is only unique within a single
  `ingest_prep()` call, not globally. Storage uses `collection.upsert()` (never
  `add()`), so re-ingesting byte-identical content overwrites in place instead of
  raising a duplicate-ID error or creating a duplicate entry. **This idempotency
  is convenient but coincidental** — it falls out of Chroma's upsert semantics,
  not a designed guarantee. Milestone 5's blockchain-registration idempotency
  needs its own explicit dedup check against on-chain state; don't assume this
  Chroma behavior extends there. A consequence of doc_hash-as-ID: if
  byte-identical chunk text appears under two different `source_file` values
  across separate `add_documents()` calls, there is only one stored Chroma
  entry and its `source_file` reflects whichever source was upserted last —
  Milestone 3's on-chain `doc_hash` lookup should not assume one Chroma entry
  maps to a unique `(source_file, chunk)` pair.
- **Collection distance space: cosine**, set via `configuration={"hnsw": {"space":
  "cosine"}}` on `get_or_create_collection()`. Verified against the real
  `chromadb==1.5.9` install rather than assumed: `collection.configuration_json`
  echoes the setting back, and a manual check with two orthogonal unit vectors
  returned `distance=1.0` (cosine) rather than `2.0` (squared-L2), confirming the
  space is actually applied, not silently defaulted. Embeddings are L2-normalized
  (Milestone 1), so cosine and L2 rank identically here regardless — this
  configuration matters for matching the spec's stated metric and for readers of
  the code, not for the actual ranking output.
- **`embedding_function=None` on every collection open**, since this project
  always supplies its own vectors via `pipeline/embeddings.py`. Verified this
  actually disables Chroma's default ONNX auto-embed (not just declines to set
  one): calling `add()` with `documents=` but no `embeddings=` raises
  `ValueError: You must provide an embedding function...`.
- **Metadata schema is locked to exactly four fields**: `source_file` (str),
  `chunk_id` (int, Milestone 1's per-call value, unchanged — NOT the Chroma ID),
  `ipfs_cid` (`""` empty-string placeholder until Milestone 4/5 wire in real values), `doc_hash` (the
  same string as the Chroma ID, `record["hash"]`). No author/publisher field —
  that identity lives on-chain in Milestone 3's `Document` struct, looked up via
  `doc_hash`. **Milestones 3-5 must populate `ipfs_cid` using this exact field
  name** when real IPFS CIDs become available.

## Milestone 3 — Blockchain Registry (2026-08-16)

- **Ownership/oracle model**: `address public owner` set to `msg.sender`
  in the constructor; constructor also auto-authorizes the deployer as
  the first oracle (`authorizedOracles[msg.sender] = true`), matching the
  spec's "Account #0 acts as Admin/Oracle" framing since Account #0 is
  the deploying account in Milestone 5's standard Hardhat workflow.
  `authorizeOracle(address, bool)` is owner-gated and lets additional
  oracles be added later without a redeploy.
- **`registerDocument` reverts on duplicate hash** rather than
  silently no-opping — protects on-chain integrity even if called
  out-of-band. Milestone 5's ingestion script is responsible for calling
  `verify_integrity()` or `get_document()` before calling
  `register_document()`, to avoid wasted gas on an expected revert. This
  is a deliberately separate, explicit check from Milestone 2's Chroma
  upsert-dedup behavior (which is coincidental idempotency, not a
  designed guarantee).
- **Publisher-per-call signing design**: `registry_client.py`'s
  `register_document(doc_hash, ipfs_cid, signing_key=None)` accepts an
  explicit signing key, defaulting to the `PRIVATE_KEY` env var (Account
  #0) only when not given. Milestone 5's ingestion script passes
  Accounts #1-#5's keys explicitly to simulate distinct publishers, since
  the spec assigns those accounts as publishers (plural, different
  accounts) — this was designed in now rather than retrofitted later.
  `update_reputation(doc_hash, delta, signing_key=None)` follows the same
  optional-override pattern but is expected to always use the
  default (oracle account), since oracle is a single designated role in
  this milestone's scope.
- **Deployment artifact handoff**: `contracts/scripts/deploy.ts` writes
  `contracts/deployments/localhost.json` (`{"address": ..., "abi": ...}`)
  on every deploy. `blockchain/registry_client.py`'s `connect()` reads
  this file directly (path computed relative to the module file), rather
  than requiring a human to copy the address into `CONTRACT_ADDRESS`
  after every fresh `npx hardhat node` restart. `contracts/deployments/`
  is gitignored (build output, like `artifacts/`/`cache/`).
- **bytes32 conversion, verified working**: `Web3.to_bytes(hexstr="0x" +
  doc_hash)` where `doc_hash` is the 64-char SHA-256 hex string from
  Milestone 1. Verified round-trip (`to_bytes(...).hex() ==
  doc_hash`) directly against the real `web3==6.20.3` install before
  writing `registry_client.py`.
- **`documentLedger`'s auto-generated getter returns the full six struct
  fields** (publisher, contentHash, ipfsCID, reputationScore, timestamp,
  isRegistered) — confirmed by compiling a scratch contract with the
  exact struct shape and inspecting the generated ABI, not assumed from
  general Solidity docs. No separate getter function was added.
  `registry_client.py`'s `get_document()` calls this auto-getter
  directly; `verify_integrity()` remains a thin wrapper on the contract's
  3-tuple `verifyIntegrity()` for the cheaper existence/reputation-only
  check. Milestone 8's audit trail UI should call `get_document()` when
  it needs `ipfs_cid`/`timestamp`, `verify_integrity()` otherwise.

## Milestone 4 — IPFS Client (2026-08-17)

- **Multiaddr-to-URL derivation, verified against a real daemon**:
  `IPFS_API_URL` (`.env.example`: `/ip4/127.0.0.1/tcp/5001`) is parsed by
  splitting on `/` into `["", "ip4", host, "tcp", port]` and building
  `http://{host}:{port}`. Confirmed against a real local Kubo 0.29.0
  daemon rather than assumed — `POST http://127.0.0.1:5001/api/v0/version`
  against the derived URL returned `200` with the daemon's real version
  JSON.
- **Fetch via the public gateway (`GET :8080/ipfs/<cid>`), not the API's
  `/api/v0/cat`**: both were confirmed working against the real daemon,
  but the gateway is a plain GET with no request body, matches the
  `.env.example` comment's implied convention ("gateway runs on port
  8080, no env var needed" — same host as the API, fixed port), and is
  the same read-only surface Milestone 8's audit trail UI would use.
  Upload still goes through the API's `/api/v0/add` (`POST`, multipart)
  since the gateway has no write path. Also confirmed live: Kubo's
  `/api/v0/*` endpoints reject `GET` with `405` — every API call,
  including reads, must be `POST`.
- **CID version confirmed CIDv0 by default** (`Qm...`), verified against
  the real daemon's `/api/v0/add` response with no `cid-version`
  parameter — matches the spec's example CID format exactly, so
  `storage/ipfs_client.py` never overrides `cid-version`.
- **`/api/v0/add` response shape confirmed live**:
  `{"Name": "...", "Hash": "Qm...", "Size": "29"}` — `Size` is a JSON
  string, not a number (only `Hash` is read, so this didn't require
  handling, but is noted for anyone touching `Size` later).
- **`IPFSError` wraps both failure classes**: non-2xx HTTP responses
  (confirmed live — a malformed or well-formed-but-missing CID returns
  `500` with a JSON `{"Message": ...}` body) and connection-level
  failures from a daemon that isn't running at all (confirmed live —
  killing the daemon and retrying produces
  `requests.exceptions.ConnectionError`, caught via its parent
  `requests.exceptions.RequestException`). Both `upload_text` and
  `fetch_text` catch both classes so no raw `requests` exception or
  stack trace ever reaches a caller.
- **Milestone 1's verbatim-hashing contract tested end-to-end through a
  real IPFS round trip, not just asserted**: `hash_chunk` is called on
  a mixed-case/irregular-whitespace string (the kind `normalize_text`
  would already have normalized before `hash_chunk` sees it) *before*
  `upload_text`, and again on the *fetched* text after a real
  `upload_text` → `fetch_text` round trip against the live daemon; the
  two hashes are asserted equal
  (`test_verbatim_hash_survives_real_ipfs_round_trip`). This is
  distinct from — and in addition to — the generic
  upload/fetch-returns-identical-text round-trip test.

## Milestone 5 — Ingestion Pipeline (2026-08-18)

- **`add_documents()` extended with `cid_by_hash: dict[str, str] | None = None`**,
  keyed by `doc_hash` (the same field already used as the Chroma ID). Overrides
  the `""` placeholder only for hashes present in the dict; defaults to `None`
  so every existing caller is unaffected. Confirmed by running
  `uv run pytest tests/test_retrieval_vector_store.py -v` after the change —
  all of Milestone 2's original tests passed with zero edits to their code,
  alongside two new direct regression tests (no-override placeholder path,
  selective-override path) added to the same file.
- **Skip-path trusts the stored `ipfs_cid` without re-running `verify_hash`.**
  `get_document()`'s six-field return already carries `ipfs_cid` — this is
  the reason Milestone 3 built the full-struct getter rather than only
  `verify_integrity()`'s three-tuple. Re-verifying every already-registered
  chunk against the live IPFS daemon on every ingestion run is redundant
  work with no new information; that kind of live audit belongs at
  query/display time (a later milestone), not ingestion time.
- **Safety-net ordering on the fresh path**: `upload_text()` →
  `verify_hash()` → `register_document()`, in that order. A `False` from
  `verify_hash()` aborts that chunk (excluded from the batch, logged to
  stderr) before `register_document()` is ever called — on-chain
  registration is effectively permanent in this MVP (no delete function),
  so the check has to happen before the write.
- **Failure isolation is per-chunk, not per-run.** The per-chunk try/except
  wraps `get_document()` as well as the fresh-upload path — a flaky/dead
  Hardhat node during the skip-check is exactly as plausible a transient
  failure as a dead IPFS daemon and gets identical treatment: logged,
  excluded from that file's batch, and the run continues to the next
  chunk/file. Only at the very end, after every file has been attempted,
  does `run_ingest()` return a nonzero exit code if anything failed — a
  corpus of 50-100 chunks (Milestone 9's scale) shouldn't die entirely over
  one transient hiccup, and a failed chunk is simply retried automatically
  on the next run since it was never registered.
- **Exception types confirmed live against a real Hardhat node, not
  guessed**: an unreachable node raises `requests.exceptions.ConnectionError`
  unwrapped (`registry_client.py` does no wrapping of its own — same
  underlying exception class Milestone 4's `IPFSError` wraps for IPFS
  connection failures); a duplicate-registration revert raises
  `web3.exceptions.ContractLogicError` (confirmed via a live
  `register_document()` call against an already-registered hash — the
  existing test in `tests/test_blockchain_registry_client.py` had used a
  bare `pytest.raises(Exception)` for this case, which this milestone's
  design work replaced with the precise type). `scripts/ingest.py`'s catch
  clause names exactly `(IPFSError, requests.exceptions.ConnectionError,
  ContractLogicError)` — never a bare `except Exception` — so a real bug
  still crashes the run instead of being silently logged as a data problem.
- **`publisher_key` defaults to a single fixed account** (Hardhat Account
  #1, matching `tests/test_blockchain_registry_client.py`'s
  `PUBLISHER_1_KEY`), overridable per invocation. No automatic round-robin
  or hash-based assignment across the spec's Accounts #1-#5 publisher
  roles — that decision belongs to Milestone 9, which will call
  `ingest.py` once per source file with deliberately curated
  `publisher_key` values once it's actually simulating which document
  comes from which source, not to this milestone's plumbing.
- **PDF extraction: `pypdf`, not PyMuPDF.** PyMuPDF is faster and more
  accurate but AGPL-3.0-licensed (commercial/closed-source use requires a
  paid Artifex license); `pypdf` is BSD-licensed and sufficient for the
  plain-prose PDFs in Milestone 9's demo corpus, where extraction speed at
  a handful of files doesn't matter. Confirmed current via a web search
  during design (2026-08-18) rather than assumed from stale knowledge —
  PyMuPDF's AGPL status and pypdf's continued active maintenance under the
  py-pdf org were both still current as of that search.
- **File-level failures receive identical isolation as chunk-level ones.**
  Both `_extract_text()` (which can fail with `UnicodeDecodeError` on bad
  UTF-8 or `pypdf.errors.PyPdfError` on corrupt PDFs) and `ingest_prep()`
  are wrapped in try/except `(UnicodeDecodeError, OSError,
  pypdf.errors.PyPdfError)`, logged and skipped individually. Originally
  only chunk-level failures in `_resolve_chunk_cid()` were caught, leaving
  file-level issues uncaught; this was identified during code review before
  merge and fixed to ensure both layers conform to the stated
  failure-isolation requirement.

## Milestone 6 — Trust-Weighted Re-ranking (2026-08-20)

- **Milestone 6 reputation read: `verify_integrity()`, confirmed over
  `get_document()`.** Re-ranking only ever needs `exists` and `reputation`
  per candidate — never `ipfs_cid` or `timestamp` — and runs on every
  query against every retrieved candidate, so the cheaper 3-tuple contract
  call is the correct choice on both grounds. `get_document()`'s six-field
  getter remains reserved for Milestone 5's skip-check and Milestone 8's
  audit UI, per the Milestone 3 design.
- **`exists=False` no longer treated as `reputation=0`.** The original
  framing called `reputation=0` the "worst case" for an unregistered
  chunk. That stopped holding once `updateReputation()`'s delta was
  confirmed unbounded (Milestone 3): `registerDocument()` assigns
  `reputation=0` to every freshly-published, not-yet-reviewed document, so
  0 is the neutral midpoint of the reputation range, not a floor. A chunk
  present in Chroma with zero on-chain record at all is a strictly weaker
  provenance signal than a registered-but-neutral chunk, so it must
  normalize below every registered candidate in its batch, including one
  sitting at exactly `reputation=0`. `normalize_reputation()` implements
  this as a hard floor: `floor = min(reputation for existing candidates in
  the batch) - FLOOR_PENALTY`, or `0 - FLOOR_PENALTY` if no candidate in
  the batch is registered. `FLOOR_PENALTY = 50` was chosen relative to the
  sigmoid's `SCALE = 10` (5 half-widths) specifically so the floor's
  normalized value saturates near 0 regardless of the batch's actual
  minimum — an earlier `FLOOR_PENALTY = 1` was rejected during design
  because it produced only a ~0.025 normalized-reputation gap, too small
  to reliably survive a realistic similarity-score gap between candidates.
  Exclusion from top-K entirely was considered and rejected: a hard floor
  keeps the scoring function total (no filtering side-channel) and keeps
  unregistered chunks visible-but-demoted, which serves both Milestone 8's
  audit UI and Milestone 10's evaluation better than silently dropping
  them.
- **Normalization: sigmoid, not min-max.** `normalized_reputation =
  1 / (1 + exp(-reputation / SCALE))`, a fixed global curve rather than a
  per-batch min-max scale, for two reasons. First, Milestone 10's
  MRR/Precision@K evaluation needs a document's trust contribution to be
  reproducible across queries — min-max would make the same document
  normalize differently depending on which unrelated candidates happened
  to land in the same top-K for a given query, conflating the document's
  own reputation with the incidental composition of that query's
  candidate set. Second, min-max degenerates (divide-by-~0) when all K
  candidates share similar or identical reputation, which needs a
  special-cased fallback that sigmoid does not. `SCALE = 10` is a named
  module-level constant in `retrieval/rerank.py`, tunable alongside
  `alpha` once Milestone 9's real poisoned corpus is available.
- **`alpha = 0.7` confirmed as the default**, implemented as a named,
  overridable parameter on `hybrid_score()` and `trust_weighted_rerank()`
  rather than an inline literal, per spec — Milestone 9 will tune it
  empirically. Note this is not a literal 70/30 share of two equally-scaled
  terms: `similarity` comes from `retrieval/vector_store.py`'s
  `1.0 - distance` against a cosine-distance Chroma collection, so its
  practical range is `[-1, 1]` (mildly negative similarities for unrelated
  text are routine with this project's embedding model), while
  `normalized_reputation` is strictly bounded to `(0, 1)` by the sigmoid.
  Keep this domain mismatch in mind when Milestone 9 tunes `alpha`
  empirically.
